Gemini 4 Carbon: Google posiciona um modelo para fluxos agênticos de longa duração

Conforme reportado em newsletter especializada publicada nesta semana [1], o Google lançou o Gemini 4 "Carbon" com foco declarado em tarefas de engenharia de longa duração e workflows agênticos sustentados. O nome segue a convenção de codinomes por elementos, e o posicionamento é claro: não é um modelo de chat, é um modelo de trabalho.

O que me chama atenção aqui é a mudança de framing competitivo. O setor parou de competir apenas em benchmarks de raciocínio e passou a competir em "quanto tempo esse modelo consegue manter contexto e produtividade em uma tarefa complexa". Para quem arquiteta sistemas com agentes autônomos, esse critério vai dominar as conversas de seleção de modelo nos próximos meses.

Um dado de contexto importante: segundo o ai.google.dev, o Google mantém hoje 85 modelos ativos na sua API. Isso é uma quantidade operacional alta, e sinaliza um portfólio fragmentado que pode complicar a tomada de decisão para equipes de desenvolvimento. Qual modelo, para qual tarefa, a qual custo? Essa pergunta ainda não tem resposta padronizada — e o Carbon é mais um item na lista.

Caveat de fonte

O Gemini 4 Carbon não tinha anúncio publicado no blog oficial do Google ao momento desta edição. A informação vem de uma newsletter com curadoria de múltiplas fontes. Recomendo confirmar em developers.googleblog.com antes de ajustar qualquer roadmap técnico.

DeepSeek V4.1-Flash: 77% no DeepSWE e um Super-Agent de codificação

O DeepSeek continua acelerando. A versão atualizada do V4.1-Flash registrou 77% de resolução de tarefas no benchmark DeepSWE v1.1 [2], contra 74,2% da versão de setembro. Para quem não acompanha, o DeepSWE mede resolução de issues reais em repositórios open source — não abstração matemática, mas engenharia de software do dia a dia.

77% significa que, em 100 issues abertas num repositório típico, o modelo consegue resolver sozinho mais de três quartos. Isso tem impacto direto na discussão sobre agentes de codificação autônomos em pipelines de CI/CD.

Além da atualização do V4.1-Flash, o DeepSeek lançou um "Super-Agent" de codificação autônoma [2]. Os detalhes técnicos ainda são limitados, mas o padrão é familiar: modelo base forte, scaffolding de agente e acesso a ferramentas como terminal, git e browser.

Reflexão prática

Para equipes Java, a pergunta operacional agora é: você vai usar apenas o modelo do seu provedor principal, ou vai considerar modelos alternativos como o DeepSeek para tarefas específicas de codificação onde o custo-performance é mais favorável? A resposta envolve avaliar latência, pricing, LGPD e onde os dados de código podem ser enviados.

Anthropic e OpenAI: mudanças de API com prazo em 30 de novembro

Dois avisos importantes chegaram esta semana — e ambos têm data de expiração no mesmo dia.

Anthropic — 30 de novembro

O Claude Sonnet 4.5 será descontinuado da API em 30 de novembro [3]. Se você tem código com "claude-sonnet-4-5" como string estática de model ID, tem menos de quatro semanas para migrar. O destino natural é o claude-sonnet-4-6 ou o claude-sonnet-5-5, dependendo do seu perfil de custo e qualidade.

Além disso, mudanças na política de uso da Anthropic estão previstas para o dia 12 de novembro. Vale revisar os termos em docs.anthropic.com antes dessa data — especialmente para casos de uso na linha de automação corporativa e processamento em lote.

OpenAI — 30 de novembro

A OpenAI vai encerrar o Agent Builder, o Evals Dashboard, a Evals API e o endpoint v1/prompts também em 30 de novembro [3]. Se você usa o Agent Builder para composição de agentes ou o endpoint de prompts via API, a migração precisa começar agora.

Ação urgente — antes de 30/11

  • Auditar todos os model IDs hardcoded nos seus serviços (buscar por claude-sonnet-4-5)
  • Verificar se há chamadas ao v1/prompts ou ao Evals API da OpenAI
  • Revisar o Agent Builder da OpenAI — se você tem agentes configurados lá, migre para a Responses API
  • Ler as atualizações de política da Anthropic em docs.anthropic.com/usage-policy

Agentic AI: o banco de dados virou protagonista de arquitetura

Uma das notícias mais técnicas da semana veio de uma entrevista publicada no SiliconANGLE em 1º de novembro [4]: arquiteturas agênticas exigem bancos de dados com características radicalmente diferentes do CRUD convencional.

O argumento é cirúrgico. Um agente autônomo emite quantidades imprevisíveis de queries por segundo — frequentemente não planejadas — e espera latências da ordem de milissegundos. O banco de dados que serve bem um aplicativo transacional convencional pode se tornar o gargalo num sistema onde o agente precisa buscar contexto, registrar estado intermediário e tomar decisões em tempo real.

Para quem arquiteta sistemas Java, isso tem implicações concretas que eu já estava observando em projetos:

  • JPA/Hibernate em modo lazy loading não serve para acesso agêntico de alta frequência
  • Bancos vetoriais (pgvector, Chroma, Weaviate) precisam estar no mesmo tier de latência que a lógica de agente
  • O padrão "buscar contexto → executar tool call → salvar resultado" precisa ser rápido o suficiente para não degradar a experiência do usuário final
  • Connection pooling agressivo e cache de embeddings passam a ser requisitos, não otimizações

Outro ponto relevante do AI Agents News Brief de 1º de novembro [2]: desenvolvedores estão implementando mecanismos de pausa antes de ações irreversíveis — enviar um e-mail ao cliente errado, executar uma transação financeira, fazer um deploy. Esse padrão "human-in-the-loop seletivo" está se consolidando como boa prática de arquitetura agêntica. Não é sobre desconfiar do modelo; é sobre gerenciar risco operacional de forma inteligente.

Faça agora

Mapear quais chamadas de banco de dados no seu agente são síncronas e bloquantes. Qualquer query que leve mais de 50ms na média é candidata a otimização ou cache.

Avalie depois

Considerar pgvector (extensão do PostgreSQL) como primeira opção de banco vetorial para projetos Java/Spring — elimina a necessidade de um banco dedicado separado.

O que pode esperar hoje

Nem tudo que aparece no feed merece atenção imediata. Dois temas recorrentes esta semana podem aguardar:

Nomes de modelos não anunciados oficialmente: "GPT-6", "Claude Duet" e variantes aparecem em agregadores de baixa autoridade sem nenhum anúncio oficial da OpenAI ou da Anthropic. Até sair algo nos blogs oficiais (openai.com/blog, anthropic.com/news), ignore. Construir sobre especulação de modelo ID é receita para retrabalho.

Se você está decidindo onde investir seu tempo de aprendizado em novembro, priorize código funcional sobre badge.

Radar Java + IA — novembro pode ser o mês do Spring AI Agents

O ecossistema Java com IA entrou num período produtivo. Spring AI e LangChain4j têm releases recentes com dinâmicas distintas, e vale entender onde cada um está.

Spring AI 2.1.0-M1 e o Spring AI Agents

A versão 2.1.0-M1 foi publicada em 25 de setembro de 2026 [5], como primeiro milestone da linha 2.1 — projetada para Spring Boot 4.x e Spring Framework 7. O dado mais significativo para este mês: o Spring AI Agents, um módulo experimental dedicado à orquestração de agentes, está previsto para lançamento em novembro de 2026. Ainda não chegou com release estável, mas é o projeto a acompanhar de perto se você está planejando arquiteturas agênticas em Java enterprise.

LangChain4j 1.22.0

O core do LangChain4j está na versão 1.22.0 (outubro de 2026), com o Spring Boot starter ainda em beta (1.22.0-beta32) [5]. A abordagem que eu acho mais pragmática para quem vem do Java tradicional: você declara um agente como uma interface Java com anotações, e o framework cuida da orquestração. Agentes podem ser compostos em fluxos sequenciais, condicionais e paralelos.

// LangChain4j 1.22.0 — dependências: dev.langchain4j:langchain4j-spring-boot-starter:1.22.0-beta32
// Requer Java 17+ e Spring Boot 3.x ou 4.x

@AiService
public interface CodeReviewAgent {

    @SystemMessage("""
        Você é um revisor de código Java especializado em segurança e performance.
        Identifique vulnerabilidades, problemas de concorrência e oportunidades de otimização.
        Responda em português do Brasil com exemplos de correção quando aplicável.
        """)
    String review(@UserMessage String diff);
}

Para projetos novos que começa hoje: se você já usa Spring Boot, minha recomendação é aguardar o lançamento do Spring AI Agents este mês antes de escolher o framework de orquestração. Se o projeto não pode esperar, o LangChain4j 1.22 é uma escolha segura com API estável no core.

Conclusão

O início de novembro confirmou a velocidade que o ecossistema de IA vem mantendo: um novo modelo do Google posicionado para agentes, o DeepSeek ampliando sua vantagem em benchmarks de engenharia de software, e dois grandes provedores encerrando serviços no mesmo dia. Para quem opera sistemas em produção, o item mais crítico desta edição é a auditoria de model IDs e endpoints — não porque a migração seja complexa, mas porque a janela de tempo está se fechando.

No Java, o ecossistema está maduro o suficiente para projetos sérios. A chegada do Spring AI Agents este mês, se confirmada, vai reduzir a resistência interna de times que ainda hesitam em adotar LLMs porque "não é coisa de Java enterprise". É.
