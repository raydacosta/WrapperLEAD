Spring AI 2.0 GA + Spring Boot 4: o stack Java para IA nativa ficou sério

Embora o GA tenha chegado em 12 de junho, só agora estão surgindo análises comparativas consolidadas sobre o que o Spring AI 2.0 significa na prática para times enterprise. Construído sobre Spring Boot 4 e Spring Framework 7, a versão 2.0 não é apenas uma atualização incremental — é uma reescrita de posicionamento. O framework saiu do papel de "biblioteca de integração com LLMs" para assumir o papel de plataforma completa para aplicações de IA.

O que me chamou mais atenção foram três mudanças estruturais: primeiro, o suporte ao Model Context Protocol (MCP) foi promovido para feature de primeira classe — não mais um addon comunitário. Segundo, o ToolCallingAdvisor tira do desenvolvedor a responsabilidade de gerenciar o loop de chamada de ferramentas (iterate → call → append → resubmit), abstraindo esse ciclo num componente reutilizável na cadeia de advisors. Terceiro, a adoção do JSpecify para null-safety em toda a API, aplicada em tempo de compilação via NullAway, que resolve uma classe inteira de bugs em tempo de desenvolvimento, não de runtime.

Para quem mantém aplicações Spring Boot 3.x, a linha 1.1.x continua com suporte ativo. A migração para Boot 4 não é obrigatória agora, mas o sinal estratégico é claro: o futuro do ecossistema Java para IA vai rodar no novo stack. Comece a planejar.

Harness Engineering: o paradigma que substituiu o Prompt Engineering em 2026

A evolução é clara quando traço a linha do tempo: em 2023, o foco era Prompt Engineering — como escrever o prompt certo para obter a resposta certa. Em 2025, evoluímos para Context Engineering — não só o prompt, mas o contexto completo que o modelo recebe: histórico, ferramentas, documentos recuperados via RAG. Em 2026, chegamos ao Harness Engineering — construir o invólucro programático que governa o ambiente de execução do agente: workflow, constraints, feedback loops, toolchain e lifecycle completo.

Essa evolução tem consequências arquiteturais diretas. Não se trata mais de otimizar um prompt em isolamento. Trata-se de desenhar um sistema determinístico que envolve o modelo probabilístico e traduz comportamento imprevisível em output confiável para produção. Empresas não podem escalar operações quando a saída do sistema depende de como o usuário formulou a pergunta — o harness resolve exatamente isso.

Do ponto de vista prático: se você ainda está focando seus esforços em "como melhorar meu prompt", você está otimizando a camada errada. O investimento deve estar na arquitetura do harness — nos contratos entre agentes, nos mecanismos de fallback, na observabilidade dos loops de decisão.

OpenAI IPO: o que o pedido de capital aberto significa pra quem usa as APIs

A OpenAI entrou com pedido de IPO buscando avaliação de até US$ 1 trilhão, trabalhando com Goldman Sachs e Morgan Stanley. A estreia na bolsa pode acontecer ainda em setembro de 2026. Para quem acompanha o mercado financeiro, é uma notícia enorme. Para quem usa a API da OpenAI em produção — como muitos dos projetos que acompanho — o sinal relevante é diferente.

Uma empresa aberta tem obrigações de transparência financeira que mudam o jogo. A OpenAI reportou prejuízo de US$ 5 bilhões em 2024 contra receita de US$ 3,7 bilhões, com custo operacional de US$ 1 bilhão por mês. Abrir capital significa expor esses números ao escrutínio público e de analistas — e a pressão por margem vai crescer. Isso pode se traduzir em revisões de precificação da API, mudanças nos tier de acesso a modelos de ponta, e aceleração na deprecação de modelos mais antigos.

Minha recomendação: quem tem workloads críticos em OpenAI deve começar agora a mapear estratégias de multi-provider. Não porque a OpenAI vá sumir, mas porque dependência de vendor único em API de IA é risco que não se justifica quando existem alternativas maduras (Anthropic, Google Gemini, e modelos open weight em infraestrutura própria).

Agentic RAG como nova baseline: o RAG ingênuo ficou para trás

Há uma análise circulando que define bem o momento atual: o RAG simples — recupera documentos, monta contexto, envia pro modelo — virou commodity. O que está se tornando a nova baseline é o Agentic RAG: o agente reformula a query em subqueries, executa múltiplas rodadas de recuperação, avalia a qualidade dos resultados e decide se precisa buscar mais antes de responder.

O que vem depois disso é ainda mais interessante: o argumento que está ganhando força é que o problema do RAG em produção não é a retrieval em si — é que o modelo gasta tokens em inference interpretando e contextualizando conhecimento que poderia ter sido pré-processado em tempo de compilação. A ideia de uma "compilation-stage knowledge layer" — processar e estruturar o conhecimento antes do momento de uso — é a direção que equipes com workloads pesados estão explorando.

ToolCallingAdvisor — Spring AI 2.0

A nova abstração que gerencia automaticamente o loop de chamada de ferramentas em agentes Spring. Estudar como integrá-lo na advisor chain é fundamental para quem quer agentes confiáveis em produção com Spring Boot 4.

🔌

Model Context Protocol (MCP) no Spring AI

MCP virou cidadão de primeira classe no Spring AI 2.0, com anotações próprias e transporte Spring-specific. Entender o protocolo e como expor tools via MCP vai ser diferencial nas próximas semanas.

🏗️

Harness Engineering — Arquitetura de Agentes

O paradigma que substituiu o Prompt Engineering. Vale estudar como desenhar o invólucro programático ao redor de agentes LLM: contratos, feedback loops, mecanismos de retry e fallback, observabilidade.

🔍

Agentic RAG com subquery decomposition

Reformulação de queries em subqueries paralelas, avaliação de relevância dos chunks recuperados e decisão iterativa de quando parar de buscar. É o que separa um RAG de demo de um RAG de produção.

⚖️

LangChain4j 1.x vs Spring AI 2.0 — quando usar cada um

Com LangChain4j na versão 1.17.2 e Spring AI 2.0 GA, ambos são produção-ready. Estudar os trade-offs de composição opinionada (Spring AI) vs blocos granulares (LangChain4j) define a escolha arquitetural certa por contexto.

💼

Estratégia multi-provider de LLM

Com o IPO da OpenAI trazendo incerteza de precificação, mapear abstração de provider — usando interfaces agnósticas como as do Spring AI ou LangChain4j — vira proteção arquitetural, não overengineering.

☕ Radar Java + IA

O ecossistema Java para IA está mais maduro do que a maioria dos desenvolvedores percebe. Temos dois frameworks de produção — Spring AI 2.0.0 GA (junho 2026) e LangChain4j 1.17.2 (julho 2026) — com suporte completo a tool calling, RAG, chat memory, vector stores e MCP. Essa coexistência não é problema; é sinal de saúde do ecossistema.

A escolha entre os dois segue uma regra prática: se seu projeto já vive no universo Spring Boot, o Spring AI 2.0 é a extensão natural — ele se integra ao ciclo de vida do container, usa Spring Beans como tools e traz o ToolCallingAdvisor para gerenciar o loop agentic. Se você precisa de controle granular sobre cada componente do pipeline de IA (DocumentLoader, DocumentSplitter, EmbeddingStore de forma independente), ou se quer evitar lock-in com o ecossistema Spring, o LangChain4j é mais adequado. Ambos suportam Anthropic Claude, OpenAI, Google Gemini e modelos locais via Ollama.

O ponto crítico do Spring AI 2.0 que merece atenção imediata é o suporte a MCP como anotação de primeira classe. Isso significa que você pode transformar qualquer Spring Bean anotado com @Tool em um servidor MCP — e qualquer cliente MCP, incluindo Claude Desktop ou agentes externos, pode descobrir e chamar essas tools. Abaixo, um exemplo mínimo de como o ToolCallingAdvisor simplifica a construção de um agente com tools no Spring AI 2.0:

// Spring AI 2.0 — Agente com ToolCallingAdvisor
@Configuration
public class AgentConfig {

    @Bean
    public ChatClient agentChatClient(ChatClient.Builder builder) {
        return builder
            .defaultAdvisors(
                new ToolCallingAdvisor(),           // gerencia o loop tool-call automaticamente
                new MessageChatMemoryAdvisor(
                    new InMemoryChatMemory()
                )
            )
            .defaultTools("catalogTools", "orderTools") // Spring Beans como tools
            .build();
    }
}

// Tool declarada como Spring Bean — descoberta automática via MCP
@Component
public class CatalogTools {

    private final ProductRepository productRepository;

    @Tool(description = "Busca produtos pelo nome no catálogo corporativo")
    public List<ProductDTO> findByName(String name) {
        return productRepository
            .findByNameContaining(name)
            .stream()
            .map(ProductDTO::from)
            .toList();
    }

    @Tool(description = "Retorna estoque disponível para um SKU específico")
    public StockDTO getStock(String sku) {
        return StockDTO.from(productRepository.findBySku(sku));
    }
}

// Uso no serviço — o advisor resolve o loop internamente
@Service
public class ProductAgentService {

    private final ChatClient agentChatClient;

    public String query(String userMessage) {
        return agentChatClient
            .prompt()
            .user(userMessage)
            .call()
            .content(); // ToolCallingAdvisor executa quantas rodadas forem necessárias
    }
}

A simplicidade acima esconde o que o ToolCallingAdvisor faz por baixo: detecta quando o modelo solicita uma tool call, executa a tool, anexa o resultado ao contexto e reenvia para o modelo — repetindo quantas iterações forem necessárias até o modelo produzir uma resposta final. Antes do Spring AI 2.0, esse loop tinha que ser implementado manualmente, o que era fonte de bugs e inconsistências entre implementações. Agora é infraestrutura.
