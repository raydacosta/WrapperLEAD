Manus AI 2.0 no Web Summit: agentes com identidade digital autônoma

A Manus apresentou no palco do Web Summit 2026, em Lisboa, uma nova versão do seu agente com capacidades que ultrapassam qualquer demonstração anterior que acompanhei: o agente recebe número de telefone próprio, endereço de e-mail e uma carteira digital habilitada para compras. Em outras palavras, estão entregando identidade digital autônoma para agentes de IA — a capacidade de existir no mundo digital como um "ator" com credenciais próprias.

Do ponto de vista arquitetural, isso levanta questões sérias que eu acho que o mercado ainda não discute com profundidade suficiente: como rastrear responsabilidade legal quando um agente com e-mail e carteira própria toma uma decisão de compra errada? Qual é o modelo de auditoria? Dito isso, o potencial para automação de processos de negócio é enorme — especialmente em fluxos que hoje exigem intervenção humana apenas por causa de canais de comunicação. Se o agente pode receber um e-mail de confirmação, responder e fechar uma transação, eliminamos um gargalo real.

Para equipes Java que trabalham com automação de processos, o que a Manus está mostrando é o estado da arte de agentes com tool calling avançado. Vale entender a arquitetura mesmo que o produto em si não seja o que você vai usar.

Akamai Inference + Agent Sandbox: edge computing entra no jogo de IA

A Akamai lançou no início de novembro dois produtos complementares: o Akamai Inference, para implantação de modelos abertos em infraestrutura edge, e o Agent Sandbox, um ambiente isolado para execução de agentes. O catálogo inicial traz 12 modelos, incluindo NVIDIA Nemotron-3 Ultra, gpt-oss-120b e Gemma 4. O que me chama atenção aqui não é o produto em si, mas o sinal estratégico: a Akamai claramente enxerga que latência de inferência em edge vai ser diferencial competitivo para agentes que precisam responder em tempo real.

Para aplicações Java que hoje chamam APIs de LLM centralizadas e sofrem com latência variável, isso abre uma alternativa interessante — especialmente para casos de uso onde o dado não pode sair da região ou onde latência sub-100ms é requisito. O sandbox de agentes também é relevante do ponto de vista de segurança: isolamento de execução é exatamente o que falta em muitas arquiteturas agenticas improvisadas que tenho visto.

Google AI Plus perde Gemini Pro em 13 de novembro: sinal de custos insustentáveis

A partir de 13 de novembro, assinantes do plano Google AI Plus perdem o acesso aos modelos Gemini Pro, mantendo apenas Flash e Flash-Lite. O Google não deu uma explicação pública clara, mas o contexto é transparente para quem acompanha o mercado: Gemini Pro e as versões mais pesadas como Gemini 4 Argon e Gemini 4 Carbon têm custo computacional que simplesmente não é sustentável em planos de assinatura fixa de baixo valor.

Isso confirma uma tendência que venho observando: as grandes plataformas estão reposicionando seus modelos mais capazes para camadas de pagamento por uso ou enterprise, enquanto os planos de assinatura migram para modelos flash/mini/haiku. Para arquitetos de solução, o recado é direto: se você está desenhando uma aplicação que depende de Gemini Pro via plano de assinatura, precisa rever o modelo de custo agora antes que a migração seja forçada.

FinOps Agêntico: de monitoramento reativo a controle autônomo de custo

O tema do FinOps para sistemas agênticos está ganhando corpo como disciplina. Um dado que me chamou atenção: agentes de IA costumam gerar entre 5 e 20 chamadas internas a LLMs por cada interação visível ao usuário — o que torna o custo real quase invisível para quem monitora apenas as chamadas externas. A resposta emergente do mercado é o "FinOps agêntico": usar agentes para monitorar e otimizar o gasto de outros agentes em tempo real, fechando o loop de forma autônoma.

O State of FinOps 2026 da FinOps Foundation indica que 98% das práticas já gerenciam gasto com IA como prioridade, e que o FinOps para agentes é o tema número um do ano. Para quem está construindo produtos em Java com LLMs, isso não é mais uma preocupação futura: é uma questão operacional que precisa de resposta arquitetural já na fase de design — trace IDs por chamada, teto de tokens por execução, profundidade máxima de loops.

☕ Radar Java + IA

O debate Spring AI 2.0 versus LangChain4j 1.20.x amadureceu consideravelmente em 2026. Já não é mais questão de preferência — é questão de adequação arquitetural. O Spring AI 2.0 GA, lançado em junho, foi construído sobre Spring Boot 4 e Spring Framework 7, e traz uma API de chat cliente opinativa e integrada que acelera muito o time-to-market para RAG padrão e chat. Se a sua stack já é Spring, o Spring AI é o caminho natural: configuração automática, integração com todos os providers principais e curva de aprendizado mínima.

O LangChain4j, agora na linha 1.20.x com releases a cada duas a quatro semanas, se posiciona de forma diferente: é agnóstico de framework (funciona com Spring Boot, Quarkus, Micronaut, Helidon ou Java puro) e expõe o pipeline de RAG como peças independentes. Isso é exatamente o que você precisa quando o RAG é o coração do produto — quando você precisa controlar o chunking, a estratégia de embedding, o retriever e o ingestor de forma granular. Para times que trabalham com Quarkus em ambientes GraalVM nativo, o LangChain4j é hoje a única opção madura.

Uma combinação que tenho visto funcionar bem em produção: Spring AI para a camada de chat e RAG padrão, e LangChain4j apenas para a camada de agentes e tool calling complexo. O risco aqui é conflito de auto-configuração quando os dois coexistem no mesmo projeto — vale isolar em módulos separados ou usar um proxy de serviço.

No que diz respeito a FinOps Java, o ponto prático imediato é instrumentar todas as chamadas ao LLM com request_id e trace_id vinculados à tarefa do agente — sem isso, você não consegue atribuir custo por fluxo e perde visibilidade sobre quais agentes estão gastando o quê. O exemplo abaixo mostra um padrão simples com LangChain4j e Langfuse para rastreamento de custo:

// Padrão de rastreamento de custo por trace com LangChain4j
ChatLanguageModel model = AnthropicChatModel.builder()
    .apiKey(System.getenv("ANTHROPIC_API_KEY"))
    .modelName("claude-haiku-5-5")
    .maxTokens(1024)
    .build();

// Registrar trace_id antes de cada chamada agentica
String traceId = UUID.randomUUID().toString();
String taskId  = "agent-task-compra-autonoma";

TokenUsage usage = model.generate(messages).tokenUsage();

// Enviar para Langfuse ou sistema de observabilidade
observabilityClient.record(
    TraceEvent.builder()
        .traceId(traceId)
        .taskId(taskId)
        .inputTokens(usage.inputTokenCount())
        .outputTokens(usage.outputTokenCount())
        .model("claude-haiku-5-5")
        .build()
);

Este padrão simples, aplicado consistentemente, dá visibilidade real sobre o custo por fluxo agentico — e é o primeiro passo para qualquer estratégia séria de FinOps com LLMs em Java.
