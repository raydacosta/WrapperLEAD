Context Architecture está substituindo o RAG como paradigma de recuperação enterprise

O VentureBeat publicou uma análise que resume bem o que tenho visto em conversas com clientes: o RAG clássico — aquele pipeline estático de chunk, embed e retrieve — está chegando no seu limite operacional quando o workload é agentic. Agentes fazem ordens de grandeza mais requisições de dados do que usuários humanos. A maioria das camadas de recuperação foi construída para o problema em escala humana. Não sobrevive ao volume agentico.

O dado que sustenta isso é concreto: a pesquisa VB Pulse RAG Infrastructure Market Tracker (Q1 2026) encontrou que a intenção de compra por recuperação híbrida triplicou — de 10,3% para 33,3% entre janeiro e março. Além disso, o investimento em otimização de recuperação passou de 19% para 28,9%, ultrapassando pela primeira vez o gasto com avaliação de modelos. O mercado está dizendo algo claro: o gargalo agora é a recuperação, não o modelo.

A conclusão prática: empresas que definirem sua Context Architecture agora — com entidades de negócio, relacionamentos e regras de acesso versionadas como infraestrutura — não vão precisar reconstruir quando o volume de agentes escalar. Isso é exatamente o tipo de decisão de arquitetura que precisa ser tomada antes do projeto, não depois.

FinOps para LLMs: semantic caching e model tiering como redutores reais de custo

A maturidade do FinOps para sistemas LLM chegou a um ponto interessante em 2026. Plataformas como Traceloop e Vantage já oferecem atribuição em tempo real por equipe, por feature e por usuário — o que permite finalmente responsabilizar times específicos por picos de custo. O dado mais relevante que encontrei: semantic caching bem configurado reduz chamadas LLM em 30–60% em produção. Não é pequeno.

As alavancas de otimização que mais importam agora são três: (1) model tiering — rotear para modelos mais baratos quando a complexidade não justifica o custo; (2) semantic caching — evitar reprocessar prompts semanticamente similares; (3) gestão de janela de contexto — cortar memória desnecessária no sistema prompt. Qualquer projeto que não tem essas três em produção está deixando dinheiro na mesa.

LangChain4j 1.x — módulo agentic como diferencial

O lançamento 1.x formalizou o módulo langchain4j-agentic, com sub-módulos dedicados a MCP (Model Context Protocol), A2A (Agent-to-Agent) e padrões agenticos comuns. Coisas que antes exigiam wiring manual agora têm suporte de primeira classe. O framework mantém a filosofia framework-agnóstica: você pode usá-lo com Spring Boot, Quarkus ou standalone. Suporta mais de 20 provedores LLM e mais de 30 vector stores — o que é relevante quando você precisa trocar de provedor sem refatoração cirúrgica.

Spring AI 1.1 — MCP nativo e Advisors API

O Spring AI 1.1, lançado em novembro de 2025, trouxe integração completa com MCP, mais de 20 backends de modelos e a Advisors API estruturada — que permite interceptar e modificar o fluxo de chamadas ao LLM de forma declarativa. Para times já imersos no ecossistema Spring, a curva de aprendizado é mínima e a integração com Spring Security, Spring Data e Spring Boot Actuator (para observabilidade) é orgânica.

Agentic RAG em Java — o que muda

Com a evolução para Context Architecture que mencionei nos destaques, o padrão de RAG em Java também precisa ser revisitado. A tendência é usar agentes como camada de orquestração de recuperação — o modelo decide dinamicamente quando e como consultar o vector store, quando fazer busca web e quando usar uma ferramenta MCP. Isso muda o design do pipeline de estático para iterativo.

// LangChain4j 1.x — Agente com suporte MCP e tool calling declarativo
@AiService
public interface AssistantAgent {
    @SystemMessage("""
        Você é um assistente técnico da Wrapper Sistemas.
        Use as ferramentas disponíveis para responder com precisão.
        """)
    String chat(@UserMessage String userMessage);
}

// Configuração com Claude Sonnet 5 + MCP client
ChatLanguageModel model = AnthropicChatModel.builder()
    .apiKey(System.getenv("ANTHROPIC_API_KEY"))
    .modelName("claude-sonnet-5-20260630")
    .build();

McpClient mcpClient = McpClient.sync(
    new StdioMcpTransport(
        new ProcessBuilder(
            "npx", "-y",
            "@modelcontextprotocol/server-filesystem",
            "/workspace/docs"
        )
    )
).build();

AssistantAgent agent = AiServices.builder(AssistantAgent.class)
    .chatLanguageModel(model)
    .tools(McpToolProvider.from(mcpClient))
    .chatMemory(MessageWindowChatMemory.withMaxMessages(20))
    .build();

// Uso direto — o framework gerencia tool calling, memória e ciclo de raciocínio
String resposta = agent.chat("Quais são os endpoints documentados no serviço de faturamento?");

Esse padrão com @AiService e McpToolProvider é o que recomendo para novos projetos. A combinação de interface declarativa + MCP client permite trocar o servidor de ferramentas sem alterar a lógica de negócio. E com o Sonnet 5 no backend, você tem adaptive thinking ativado por padrão — sem necessidade de configurar manualmente o modo de raciocínio.
