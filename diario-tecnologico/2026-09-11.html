EU AI Act: deixou de ser regulatório para virar operacional

Em 30 de agosto de 2026, o European AI Office iniciou formalmente a primeira onda de auditorias presenciais de sistemas de IA classificados como alto risco sob o EU AI Act. Os setores alvo da primeira rodada são diretos: triagem automatizada de currículos, análise automatizada de crédito e triagem médica. Não são setores periféricos — são os casos de uso enterprise mais comuns nos últimos três anos.

O que está sendo exigido nas auditorias é operacional, não teórico: documentação técnica atualizada, diagramas de arquitetura detalhados, logs de governança de dados, fluxogramas de supervisão humana e registros de gestão de risco. Em paralelo, setembro de 2026 marca uma onda regulatória simultânea em EU, Estados Unidos, Brasil, Índia e China — cada um com seus próprios requisitos e prazos, criando um cenário de compliance fragmentado que afeta qualquer empresa com operação global.

Minha leitura direta: se você está construindo sistemas de decisão automatizada para o mercado europeu e não tem um risk register atualizado com seus respectivos controles, você não está atrasado — você está descoberto. O prazo das obrigações de alto risco foi agosto de 2026. As auditorias já começaram.

O gap de 37 pontos que silenciosamente destrói sistemas agenticos

Um dado publicado essa semana por equipes com agentes em produção resume o estado atual do mercado de forma brutal: 89% dos times implementaram observabilidade em seus sistemas agenticos, mas apenas 52% têm frameworks de avaliação (evals). Um gap de 37 pontos percentuais entre saber o que o agente está fazendo e saber se ele está fazendo certo.

A analogia que uso internamente: observabilidade sem evals é como monitorar o tempo de resposta de um endpoint sem nunca verificar se a resposta está correta. Você sabe que o sistema está rodando; não sabe se está respondendo com qualidade. Em sistemas RAG, isso se traduz em alucinações que chegam ao usuário sem nenhum sinal de alerta.

A direção clara para 2026 é evals contínuas em produção com LLM-as-judge scoring e OpenTelemetry como padrão de instrumentação. Para RAG pipelines, o Ragas oferece métricas de referência sem necessidade de ground-truth manual: faithfulness, answer relevance, context precision e context recall. Se você ainda não tem nada disso em produção, comece aí.

AccuKnox AgentZ: governança de agentes como produto — o timing importa

Em 27 de agosto, a AccuKnox anunciou o AgentZ — uma plataforma que consolida o ciclo de vida completo de agentes IA em um único stack: construção, execução, ferramentas, fluxos de trabalho, permissões e governança. A proposta não é nova tecnicamente, mas a entrega como produto unificado é relevante.

O timing não é coincidência. Com as primeiras auditorias do EU AI Act focando justamente em sistemas automatizados de decisão, a pergunta "como você controla o que seu agente pode fazer?" deixou de ser arquitetural para se tornar regulatória. Audit trail, permissões granulares e explicabilidade não são opcionais em sistemas de alto risco — são evidência de compliance.

Para equipes Java: LangChain4j e Spring AI oferecem hooks para construir essas camadas de governança, mas elas precisam ser projetadas explicitamente. Não surgem por padrão. Se você está avançando com agentes em produção, reserve um sprint para mapear os controles de permissão e auditoria do seu stack antes que um auditor externe a pergunta por você.

☕ Radar Java + IA

O ecossistema Java com IA chegou ao ponto de maturidade que eu esperava ver em 2026. Spring AI 2.0, lançado em junho com alinhamento ao Spring Boot 4, e LangChain4j na série 1.10.x formam uma dupla complementar que cobre qualquer cenário enterprise sem comprometer a robustez: RAG com múltiplas vector stores, tool calling nativo, suporte a MCP, memória conversacional, streaming e observabilidade.

A escolha entre os dois frameworks continua sendo uma questão de contexto. Spring AI é a opção natural para times que já vivem no ecossistema Spring — beans anotadas com @AiService se integram ao contexto familiar, e o roteamento de modelos usa os abstractions que o time já conhece. LangChain4j é mais explícito e mais maleável: você constrói a pipeline diretamente, o que facilita debug e customização fina de retrieval. Para arquiteturas de agentes complexos, essa transparência tem valor.

O ponto que chama minha atenção hoje, no contexto do gap de evals discutido acima: ambos os frameworks têm hooks para instrumentação, mas nenhum entrega uma camada de avaliação pronta. Você precisa construí-la. Para RAG, o Ragas funciona independente de framework Java — a avaliação é feita sobre os pares (pergunta, contexto recuperado, resposta gerada) e pode ser orquestrada via chamada direta à API. O exemplo abaixo é o padrão base que uso internamente para RAG em produção:

// LangChain4j 1.10.x — Pipeline RAG com PgVector e threshold de relevância
@AiService
interface AssistenteTecnico {
    @SystemMessage("""
        Você é um arquiteto de software especialista em Java e IA.
        Responda apenas com base no contexto fornecido.
        Se o contexto não contiver a informação, diga que não sabe.
        """)
    String consultar(@UserMessage String pergunta);
}

// Vector store — PgVector (PostgreSQL com extensão pgvector)
EmbeddingStore<TextSegment> vectorStore = PgVectorEmbeddingStore.builder()
    .host(env.getProperty("DB_HOST"))
    .port(5432)
    .database("wrapperlead_kb")
    .table("document_embeddings")
    .dimension(1536)
    .build();

// Retriever com threshold mínimo de similaridade coseno
ContentRetriever retriever = EmbeddingStoreContentRetriever.builder()
    .embeddingStore(vectorStore)
    .embeddingModel(embeddingModel)
    .maxResults(5)
    .minScore(0.75)  // calibre com seus dados — começo em 0.70
    .build();

// AiService com RAG, memória e model configurado
AssistenteTecnico assistente = AiServices.builder(AssistenteTecnico.class)
    .chatLanguageModel(chatModel)
    .contentRetriever(retriever)
    .chatMemory(MessageWindowChatMemory.withMaxMessages(10))
    .build();

O detalhe crítico aqui é o minScore(0.75). A maioria dos tutoriais não define um threshold mínimo de relevância — o resultado é contexto de baixa qualidade sendo injetado no prompt, o que degrada as métricas de faithfulness sem nenhum sinal visível. Em produção, calibre esse valor com seus dados reais: use o Ragas para medir context precision antes e depois de ajustes e trate o threshold como parâmetro de configuração, não como constante no código.

Com a queda do preço de cache-read do Fable 5.1 para $0,25 por milhão de tokens, o modelo agora compete diretamente nos cálculos de FinOps para pipelines RAG de alto volume. Vale rever os custos projetados de qualquer projeto que use Anthropic como backend principal.

O que levo deste dia é que os dois maiores riscos nos projetos de IA que acompanho não são técnicos — são de processo. O primeiro é a falta de avaliação em produção: times que observam o agente mas não medem se ele está certo. O segundo é a despreparação para conformidade regulatória: empresas que trataram o EU AI Act como problema futuro até o futuro chegar em forma de auditor.

Modelos mais avançados — Fable 5.1, GPT-6 Astra — não resolvem nenhum dos dois. Eles amplificam o que você já tem. Se o que você tem é um pipeline sem evals, você tem um pipeline mais rápido e mais barato de cometer os mesmos erros.

Se você está construindo com agentes, reserve tempo essa semana para instrumentar ao menos uma métrica de avaliação em produção. E se você atende o mercado europeu, abra o EU AI Act e classifique seus sistemas antes que o European AI Office faça essa pergunta por você.
