Anthropic lança Message Threads Beta na API — agentes 35% mais rápidos

No dia 2 de novembro, a Anthropic colocou o Message Threads em beta público na Messages API. A ideia é simples mas o impacto é direto: em vez de reenviar a conversa inteira a cada turno, o cliente envia apenas as novas mensagens mais o ID da resposta anterior. O servidor retém o contexto por até 5 minutos entre requisições.

Para agentes com histórico muito longo — conversas entre 500 mil e 1 milhão de tokens — a queda no tempo até o primeiro token chega a 35% segundo a Anthropic. Custo de tokens: inalterado. O Claude ainda lê tudo na memória a cada turno; o ganho é só no overhead de transmissão e parsing HTTP.

Já está ativo por padrão para usuários do Claude Code. Para ativar via API direta, basta adicionar o cabeçalho message-threads-2026-08-12 e passar um campo thread. Os SDKs oficiais expõem client.beta.messages.thread(...). Atenção: threads não são elegíveis para zero data retention nem para configurações HIPAA.

OpenAI, Google, Microsoft e Anthropic se unem para novo token robots.txt

As quatro grandes do setor anunciaram suporte a um token compartilhado no robots.txt que permite que publishers optem por não ter seu conteúdo usado para treino de modelos de IA. É o movimento mais coordenado que vi até agora entre empresas que são concorrentes diretas.

📚 O que vale estudar hoje

Com base no que acompanhei hoje, estes são os temas e recursos que recomendo explorar:

🧵 Message Threads API

Leia a documentação oficial da Anthropic sobre o beta do Message Threads. Entender o ciclo de vida de 5 minutos e o campo thread vai te preparar para usar isso em produção quando o GA chegar.

🔍 Agentic RAG — Padrões 2026

O FutureAGI tem um guia atualizado sobre os 6 padrões de Agentic RAG (router, corrective, self-RAG, adaptive, GraphRAG). Vale estudar o corrective RAG em particular — funciona bem com agentes que usam ferramentas de verificação.

☕ LangGraph4j

A versão Java do LangGraph permite construir workflows de agentes como grafos de estado. É framework-agnóstico: funciona com LangChain4j e Spring AI. Se você já usa um dos dois, vale adicionar LangGraph4j para orquestração mais complexa.

🌱 Spring AI 2.0 — MCP na prática

O Spring AI 2.0 GA, lançado em junho/2026, trouxe suporte de primeira classe ao MCP com transportes STDIO, SSE e Streamable-HTTP. Se sua stack é Spring Boot 4+, esse é o ponto de entrada mais direto para expor ferramentas como servidores MCP.

🔭 Observabilidade em Agentes

Langfuse, Arize Phoenix e LangSmith são as três ferramentas mais citadas em 2026 para rastrear chamadas de ferramentas, trajetórias e custos de agentes em produção. Vale entender qual se integra melhor ao seu stack antes de ir para produção.

💰 FinOps com LLMs

Com a Anthropic abrindo capital e a pressão por eficiência crescendo, rastrear custo por trajetória de agente vai ser cada vez mais cobrado. Estude cost-aware planning: a prática de estimar tokens antes de executar uma cadeia longa.

☕ Radar Java + IA

O ecossistema Java com IA continua acelerando em novembro de 2026, e os dois principais frameworks estão em trajetórias muito claras:

Spring AI 2.0 (GA desde junho/2026) — construído sobre Spring Boot 4 e Spring Framework 7, com Java 17 como mínimo. O diferencial da versão 2.0 é o suporte nativo ao MCP com os três transportes principais: STDIO, SSE e Streamable-HTTP. Se você já tem uma stack Spring Boot, expor suas ferramentas como um servidor MCP nunca foi tão simples.

LangChain4j 1.20.x — o projeto continua com releases mensais. As adições recentes que me chamaram atenção são o HibernateContentRetriever para RAG (você consegue usar seu JPA existente como fonte de recuperação) e o suporte ao protocolo A2A (agent-to-agent), que o Spring AI ainda não tem. Para stacks não-Spring como Quarkus ou micronaut, LangChain4j continua sendo a escolha mais sólida.

LangGraph4j — uma biblioteca separada que implementa a abordagem de grafos de estado do LangGraph para Java. Funciona como camada de orquestração sobre LangChain4j ou Spring AI. Recomendo estudar se você está construindo agentes com múltiplos caminhos de decisão — o modelo de grafo é muito mais claro para representar fluxos complexos do que cadeias lineares.

Um trecho de como ficou um agente simples com LangChain4j 1.20.x e HibernateContentRetriever:

// LangChain4j 1.20.x — RAG com Hibernate como fonte de recuperação
// Dependência: dev.langchain4j:langchain4j-hibernate:1.20.0

ContentRetriever retriever = HibernateContentRetriever.builder()
    .entityManagerFactory(emf)
    .entityClass(KnowledgeBase.class)
    .embeddingModel(embeddingModel)
    .maxResults(5)
    .build();

RetrievalAugmentor augmentor = DefaultRetrievalAugmentor.builder()
    .contentRetriever(retriever)
    .build();

Assistant assistant = AiServices.builder(Assistant.class)
    .chatLanguageModel(model)
    .retrievalAugmentor(augmentor)
    .build();

O HibernateContentRetriever é particularmente útil em projetos que já têm um modelo de domínio robusto em JPA — você não precisa duplicar dados em um vector store separado para começar com RAG.
