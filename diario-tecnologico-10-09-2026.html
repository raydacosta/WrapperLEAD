Claude Fable 5.1 e Mythos 5.1: cache 75% mais barato e watermarks obrigatórios

A Anthropic lançou em 1º de setembro o Claude Fable 5.1 e o Claude Mythos 5.1, dois modelos que compartilham a mesma base mas possuem envelopes de segurança distintos. O que me interessa diretamente como arquiteto é a mudança de preço: o cache de prompt caiu de US$ 1,00 para US$ 0,25 por milhão de tokens — uma redução de 75%. O preço de entrada e saída de tokens permanece o mesmo (US$ 10/M e US$ 50/M, respectivamente), mas o custo de reuso de contexto em RAG e em fluxos multi-turn caiu dramaticamente. Para sistemas com janelas de contexto grandes e chamadas repetitivas — que é exatamente o perfil do que construímos na Wrapper — isso impacta o FinOps de forma direta.

O Fable 5.1 também anuncia 60% menos falsos positivos em segurança para usuários do Claude Code, o que é relevante para quem usa o modelo como co-piloto de desenvolvimento. E há uma novidade regulatória significativa: Fable 5.1 e Mythos 5.1 são os primeiros modelos Claude com watermarks invisíveis em texto e arquivos, em conformidade com o EU AI Act. Isso vai se tornar padrão de mercado nos próximos meses — e qualquer sistema que gere conteúdo a ser publicado precisa começar a levar isso em conta na arquitetura de output.

O Mythos 5.1 é um capítulo separado: trata-se da versão de uso restrito, disponível apenas para organizações aprovadas em cibersegurança e ciências da vida. Ele carrega as capacidades ofensivas mais avançadas do ecossistema Anthropic — análise de caminhos de exploração, descoberta de vulnerabilidades em profundidade — e fica de fora do acesso geral por boas razões. Para quem trabalha em segurança enterprise, vale acompanhar o programa de acesso trusteado.

GPT-6 Astra, Gemini 3.8 Flash e a semana do "model fatigue"

Em 3 de setembro, dois dias após a Anthropic, a OpenAI entrou em campo com o GPT-6 Astra — descrito pela própria empresa como "o mais capaz e alinhado até hoje". No mesmo período, o Google movimentou o Gemini 3.8 Flash, seu modelo voltado para latência baixa e custo reduzido. A CNBC e outros veículos descreveram esse momento como model fatigue: a fadiga do mercado diante de múltiplos lançamentos simultâneos, cada um afirmando ser o melhor.

Minha leitura pragmática: o GPT-6 Astra ainda não tem benchmarks independentes comparativos publicados com tempo suficiente para análise séria. "Mais alinhado" sem especificidade técnica é marketing. O que vale acompanhar é o posicionamento de preço e a integração com ferramentas de agentic coding, que é onde as batalhas reais de adoção acontecem. O Gemini 3.8 Flash, por outro lado, é mais direto — latência reduzida, custo agressivo, contexto grande. É o tipo de modelo que entra na camada de roteamento inteligente: usa-se o Flash para triagem e o Fable ou Astra para raciocínio complexo.

A tendência que fica desta semana é a abordagem multimodelo em produção: nenhuma empresa enterprise saudável vai rodar tudo em um único provider. A pergunta certa não é "qual o melhor modelo?", mas "qual modelo para qual etapa do pipeline?".

LangChain4j 1.19.0: protocolo MCP 2026-07-28 e transporte Streamable HTTP

O LangChain4j chegou à versão 1.19.0 em 14 de agosto, com uma atualização importante para quem trabalha com agentes Java: o cliente MCP foi atualizado para o protocolo 2026-07-28, que introduz o transporte Streamable HTTP como padrão. O SSE (Server-Sent Events), que era o mecanismo de transporte remoto até então, está oficialmente depreciado. Isso afeta qualquer integração Java que conecte agentes LangChain4j a servidores MCP — a migração precisa acontecer antes que os servidores descontinuem o SSE.

A direção do time em 2026 é clara: aprofundar as capacidades agentic (ferramentas multi-step, loops de planejamento, MCP) e melhorar a história de observabilidade. Versão 1.17.2 foi a referência de julho; 1.19.0 chegou com esse salto no protocolo. Para quem ainda está em versões 0.x ou 1.0.x, a estabilização da linha 1.x é o sinal de que é hora de migrar.

AI Observability em 2026: OpenTelemetry, LLM-as-Judge e FinOps integrado

A observabilidade de agentes de IA está se tornando tão crítica quanto a observabilidade de microserviços era em 2018. O que está emergindo em 2026 como padrão de mercado é o uso de OpenTelemetry para telemetria vendor-neutral de agentes, com rastreamento de fluxos não-determinísticos e multi-step. Ferramentas como Langfuse e AgentOps estão amadurecendo, entregando mais de 50 métricas que cobrem desde G-Eval e faithfulness de RAG até verificação de uso correto de ferramentas por agentes.

O componente de FinOps está diretamente integrado à observabilidade: o custo de tokens de reasoning e output cresce de forma desproporcional em sistemas agentic, e a granularidade de rastreamento por chamada, por usuário e por pipeline é o que permite controle real de orçamento. Para quem constrói sistemas enterprise, essa integração observabilidade + FinOps não é opcional — é a diferença entre um PoC interessante e um produto sustentável.

LangChain4j 1.19.0 — O que mudou

A versão 1.19.0, lançada em 14 de agosto, tem dois pontos principais para quem trabalha com agentes: (1) o cliente MCP foi atualizado para o protocolo 2026-07-28 com suporte ao transporte Streamable HTTP; (2) melhorias nos loops de planejamento de agentes multi-step. O SSE como transporte remoto está depreciado — se você está conectando agentes Java a servidores MCP remotos, é hora de migrar. A boa notícia é que a API de configuração do cliente não mudou dramaticamente; é principalmente uma troca de transport builder.

// LangChain4j 1.19.0 — Conectando a servidor MCP remoto via Streamable HTTP
// Substitui o SSEMcpTransport depreciado

McpTransport transport = new HttpMcpTransport.Builder()
    .url("https://seu-mcp-server.com/mcp")
    .build();

McpClient mcpClient = new DefaultMcpClient.Builder()
    .transport(transport)
    .build();

mcpClient.initialize();

List<ToolSpecification> tools = mcpClient.listTools();

ChatLanguageModel model = AnthropicChatModel.builder()
    .apiKey(System.getenv("ANTHROPIC_API_KEY"))
    .modelName("claude-fable-5-1-20260901")
    .build();

Assistant assistant = AiServices.builder(Assistant.class)
    .chatLanguageModel(model)
    .tools(tools)
    .build();

Spring AI 2.0 vs LangChain4j 1.19 — Quando usar cada um

A divisão prática que estou usando nos projetos da Wrapper: se o projeto já está em Spring Boot 4, o Spring AI 2.0 é o caminho natural — integração nativa com o ecossistema Spring, observabilidade integrada com Micrometer/OTel, auto-configuração por propriedades. Para projetos em Spring Boot 3.x, Quarkus, Micronaut ou Java puro, o LangChain4j é a escolha mais segura — suporte mais amplo de providers, mais controle explícito do pipeline, comunidade que publica versões mensais. Não existe resposta universal; existe o contexto certo para cada ferramenta.

O impacto do Fable 5.1 no custo de sistemas Java em produção

Para sistemas RAG Java que usam a API da Anthropic com prompt caching habilitado, a redução de 75% no custo de cache read é direta. Se você cacheia system prompts longos (documentos de referência, schemas, instruções de raciocínio), o custo dessas leituras caiu de US$ 1,00 para US$ 0,25 por milhão de tokens. Em um sistema com volume médio de requisições, isso representa uma redução material na conta mensal de API — e justifica revisar qualquer pipeline que ainda não esteja usando prompt caching estrategicamente.
