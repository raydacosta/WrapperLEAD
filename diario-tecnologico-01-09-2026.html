Setembro começa com o ecossistema de IA em ritmo de consolidação. Não é mais sobre "qual modelo vai surgir agora" — é sobre como arquiteturas maduras, frameworks estáveis e adoção corporativa estão se encontrando em velocidade que poucos previram no início do ano. Se em 2024 estávamos no modo descoberta, e em 2025 no modo experimentação, 2026 é claramente o ano da execução. As peças estão no tabuleiro. O jogo agora é jogar bem.

Do lado da Anthropic, o Claude Opus 5 — lançado em julho — recebeu sua segunda atualização de agosto com ganhos reais de velocidade e capacidade de raciocínio científico. Do lado Java, a situação é ainda mais animadora: o Spring AI 2.0 foi ao ar em junho direcionado ao Spring Boot 4, e o LangChain4j chegou à versão 1.17.2. Pela primeira vez sinto que o ecossistema Java para IA não está correndo atrás do Python — ele está propondo sua própria abordagem, com tipagem forte, injeção de dependência e os padrões que a indústria enterprise já conhece e confia.

Um dado que vale frisar: a KPMG mediu que mais de 26% das organizações já implantaram algum tipo de agente de IA — mais que o dobro de um ano atrás. Isso não é mais tendência de laboratório. É operação real, com custo real, com risco real. E é exatamente aí que o ecossistema Java se encaixa como uma luva: maturidade, rastreabilidade, integração enterprise e uma cultura de engenharia que não perdoa código frágil.

Spring AI 2.0 — Integração Nativa com Spring Boot 4 e Null-Safety em Tempo de Compilação

O Spring AI 2.0, lançado em junho de 2026, representa uma mudança de geração no ecossistema Java com IA. Além da migração para o Spring Boot 4, a novidade técnica mais relevante é a adoção plena de anotações JSpecify para null-safety em tempo de compilação, verificadas pelo NullAway. Traduzindo: você vai saber em build time que aquele prompt template não aceita null antes de descobrir isso em produção às 3h da manhã.

O Spring AI 2.0 também expande o suporte ao MCP (Model Context Protocol), que está se tornando o padrão de facto para interoperabilidade entre agentes e ferramentas externas — tanto o Spring AI quanto o LangChain4j implementam MCP, o que significa que suas ferramentas customizadas podem ser consumidas por qualquer framework compatível. Isso é uma mudança de paradigma: você está construindo componentes interoperáveis, não ilhas isoladas.

LangChain4j 1.17.2 — Cadência Mensal Mantida, Ecosystem Maduro

O LangChain4j chegou à versão 1.17.2 em julho de 2026, mantendo sua cadência de releases mensais desde que estabilizou na versão 1.0 GA em maio de 2025. A versão atual traz refinamentos nas integrações com os principais provedores de LLM e expansão do suporte a vector stores — incluindo melhorias no gerenciamento de chat memory para agentes de longa duração. O projeto confirmou que não é um port do Python: é uma implementação Java-first com idiomática Java forte.

O ponto que merece atenção é a comparação direta com o Spring AI 2.0: ambos têm Boot starters, RAG, tool calling e MCP. A decisão entre eles hoje é mais cultural do que técnica — Spring AI faz mais sentido se seu time já vive no ecossistema Spring; LangChain4j oferece mais flexibilidade para times que querem controle granular sem opinionation de framework.

☕ Radar Java + IA

O ecossistema Java para IA atingiu um nível de maturidade que não deixa mais desculpa para times enterprise continuarem na postura de "vamos esperar o mercado se estabilizar". Ele se estabilizou. Spring AI 2.0 e LangChain4j 1.17.x são as duas escolhas maduras, cada uma com filosofia distinta, e ambas prontas para produção.

A decisão prática hoje: se seu time já usa Spring Boot e quer a menor fricção possível, Spring AI 2.0 é a escolha natural — o ChatClient abstrai providers, os Advisors encapsulam RAG e memória, e o suporte a null-safety em compile time é exatamente o tipo de garantia que times Java exigem. Se você precisa de controle fino sobre o pipeline — definir exatamente como cada passo de embedding, retrieval e geração se conecta — o LangChain4j oferece essa granularidade sem opinionation excessiva.

O MCP (Model Context Protocol) merece atenção especial: ambos os frameworks já exportam e consomem ferramentas via MCP, o que significa que uma ferramenta que você implementa em Java pode ser usada por um agente Python, por um cliente Claude Desktop ou por qualquer orquestrador compatível. Esse é o tipo de interoperabilidade que elimina silos entre times e plataformas.

Exemplo: RAG com Spring AI 2.0 e MCP Tool Export

// Spring AI 2.0 — RAG com advisor e tool MCP
@Configuration
public class RagConfig {

    @Bean
    public ChatClient chatClient(
            ChatClient.Builder builder,
            VectorStore vectorStore) {

        return builder
            .defaultAdvisors(
                new QuestionAnswerAdvisor(vectorStore,
                    SearchRequest.defaults()
                        .withTopK(5)
                        .withSimilarityThreshold(0.75)))
            .build();
    }
}

// Expondo uma ferramenta via MCP
@Service
public class DocumentSearchTool {

    @Tool(description = "Busca documentos internos por relevância semântica")
    public List<String> searchDocuments(
            @ToolParam("query") String query,
            @ToolParam("maxResults") int maxResults) {
        // implementação com VectorStore
        return vectorStore.similaritySearch(
            SearchRequest.query(query).withTopK(maxResults))
            .stream()
            .map(Document::getContent)
            .toList();
    }
}

O padrão acima é o que estou usando em projetos da Wrapper Sistemas. A separação entre configuração de RAG (via advisor) e exposição de ferramentas (via MCP) mantém o código limpo e permite que os mesmos componentes sejam reusados em diferentes pipelines agenticos — sem duplicação, sem acoplamento desnecessário.
